    Documento de Requisitos --- MVP Fake News Fact Checker com BKT

    1. Objetivo do sistema

    O sistema oferece uma experiência gamificada de avaliação crítica de notícias e informações. Ao longo de partidas com múltiplas rodadas, o usuário responde a questões que avaliam habilidades específicas de análise da informação. O sistema registra as respostas e utiliza Bayesian Knowledge Tracing (BKT) para estimar a evolução do domínio de cada habilidade ao longo do tempo.

    O MVP deve entregar um fluxo persistente de ponta a ponta: notícias armazenadas no banco são associadas a questões válidas; o usuário responde; o backend determina a correção; o BKT atualiza a estimativa da habilidade avaliada; e o sistema utiliza o estado atualizado para selecionar questões futuras e apresentar um perfil de habilidades.

    A integração existente com a Google Fact Check API e as funcionalidades de verificação podem continuar disponíveis como recursos complementares. Elas não substituem o BKT: a verificação externa fornece informações sobre alegações e verificações publicadas, enquanto o BKT estima o domínio de habilidades do usuário com base em suas respostas.

    2. Escopo do MVP

    2.1. Incluído

    • Persistência de notícias provenientes dos datasets do projeto.
    • Importação repetível e validada de notícias para o banco de dados.
    • Cadastro e persistência de questões associadas às notícias.
    • Classificação de cada questão em uma única habilidade.
    • Definição de gabarito, explicação e dificuldade para cada questão.
    • Partidas com até dez rodadas.
    • Registro de respostas, confiança declarada e tempo de resposta, quando disponíveis.
    • Atualização e persistência do estado BKT por habilidade.
    • Seleção determinística de questões, priorizando a habilidade com menor domínio estimado.
    • Evitar repetição de questões respondidas enquanto existirem alternativas elegíveis.
    • Feedback após a resposta e perfil com as quatro habilidades.
    • Autenticação e autorização para proteger jogos, respostas e estados de habilidade.
    • Testes unitários e de integração do fluxo principal.
    • Preservação das funcionalidades existentes de verificação factual, quando compatíveis com a arquitetura atual.

    2.2. Fora do escopo obrigatório

    • Treinar um classificador próprio para decidir se uma notícia é verdadeira ou falsa.
    • Estimar automaticamente parâmetros BKT a partir de dados coletados. Os parâmetros iniciais podem ser configurados e documentados.
    • Tratar as 24.800 notícias como questões prontas.
    • Gerar automaticamente questões para todas as notícias sem validação.
    • Reinforcement Learning, Deep Knowledge Tracing (DKT), K-Means ou outros algoritmos adaptativos complexos.
    • Diagnosticar personalidade, ideologia ou suscetibilidade psicológica do usuário.
    • Pipeline contínuo de MLOps ou retreinamento automático.
    • Dependência obrigatória de LLM para iniciar ou executar uma partida.
    • Análise multimodal avançada, busca reversa de imagem ou CLIP como requisito para o fluxo principal do jogo. Funcionalidades existentes podem ser preservadas, mas não devem bloquear o jogo.

    3. Conceitos e entidades principais

    3.1. Notícia (News)

    Armazena o conteúdo original utilizado para compor questões. Deve preservar, quando disponíveis, título, texto, URL, origem/publicador, classificação original, data e referência à imagem.

    A classificação de origem da notícia é distinta da resposta do usuário e de qualquer resultado retornado por uma API de fact-checking.

    3.2. Questão (Question)

    Representa uma atividade que utiliza uma notícia para avaliar uma habilidade. Uma notícia pode estar associada a várias questões, e cada questão deve avaliar uma única habilidade.

    Cada questão válida deve possuir notícia associada, habilidade associada, enunciado, alternativas, gabarito, explicação e dificuldade numérica entre 0 e 1. O gabarito e a explicação não devem ser enviados ao frontend antes do envio da resposta.

    3.3. Habilidades (Skill)

    • SOURCE: avaliar origem, rastreabilidade e confiabilidade da fonte.
    • EVIDENCE: avaliar se as evidências sustentam a alegação.
    • CONTEXT: identificar omissões, distorções ou uso de informação fora de contexto.
    • VISUAL: avaliar se uma imagem disponível corresponde à alegação e constitui evidência relevante.

    Uma questão só deve avaliar uma habilidade. Não se deve atualizar várias habilidades a partir de uma única resposta no MVP.

    3.4. Estado de habilidade (UserSkillState)

    Armazena, por usuário e habilidade, a probabilidade atual estimada de domínio (mastery_probability) e a data da última atualização. Deve existir no máximo um estado atual por combinação de usuário e habilidade. Os valores devem permanecer entre 0 e 1 e ser persistidos entre partidas e reinicializações.

    3.5. Partida e rodada (Game, GameRound)

    Game representa uma partida do usuário. GameRound representa uma rodada daquela partida e referencia a notícia apresentada. A questão efetivamente respondida deve ser identificada de maneira inequívoca pelo registro de resposta.

    3.6. Resposta (Answer)

    Armazena, no mínimo, usuário, rodada, questão, alternativa selecionada, correção calculada pelo backend e data/hora. Confiança declarada e tempo de resposta podem ser armazenados quando disponíveis. O backend determina a correção.

    7. Critérios de aceite ponta a ponta

    O MVP será considerado funcional quando:

    1. O banco é inicializado e as quatro skills existem sem duplicação.
    2. Um subconjunto do dataset é importado e a reexecução não duplica registros.
    3. Existem questões válidas persistidas e associadas a notícias importadas.
    4. Um usuário autenticado inicia uma partida e recebe uma questão elegível.
    5. A API apresenta enunciado e alternativas sem revelar o gabarito.
    6. O usuário envia uma resposta e o backend determina a correção.
    7. A resposta é persistida e a habilidade correspondente é atualizada pelo BKT exatamente uma vez.
    8. O perfil retorna as quatro estimativas persistidas.
    9. A próxima seleção utiliza o estado atualizado e evita repetir questões respondidas quando há alternativas.
    10. O sistema apresenta feedback e encerra a partida após dez rodadas respondidas ou antes, se não houver questões elegíveis.
    11. Histórico e perfil permanecem disponíveis após reinicialização do backend.
    12. Os testes do backend passam e o frontend compila com tipos alinhados à API.

    8. Dados e limitações metodológicas

    A base atual contém aproximadamente 22 mil notícias falsas e 2.800 verdadeiras. Esses registros são fontes de conteúdo, não um banco de questões pronto.

    A importação deve preservar a origem e a classificação original. As questões precisam ser elaboradas ou curadas com base nas informações disponíveis. Não se deve inferir que uma notícia possui imagem, fonte verificável ou evidência suficiente apenas porque existe no dataset.

    O MVP deve começar com um conjunto controlado de questões revisadas, suficiente para exercitar as quatro habilidades e concluir partidas de teste. A cobertura integral do dataset pode ocorrer incrementalmente.

    Quando houver material válido, o conjunto deve incluir notícias classificadas como verdadeiras e falsas. O sistema não deve permitir que responder sempre "falso" seja uma estratégia suficiente para obter bom desempenho.

    A qualidade do BKT depende da validade dos enunciados, gabaritos e associações entre questões e habilidades. A calibração dos parâmetros com interações reais é uma possível evolução de pesquisa, não um requisito para concluir o MVP.
